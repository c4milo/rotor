# The instruction gate's baseline: rotor's own instructions per iteration of each workload of
# bench/work/work.zig, which bench/work/work_gate.zig counts and holds here (CLAUDE.md, Commands).
#
# One section per machine, `<os>-<arch>-<backend>`. A count over its line by more than the
# tolerance fails the gate; a count under it by more asks for the line to be lowered. The programs
# are built for the baseline processor of each architecture, so a section holds for every machine
# of it. A machine the file has no section for is held to nothing, and the gate prints the section
# to add, which is how the Linux sections are to be taken: from CI's first run on each runner.
#
# macos-aarch64-kqueue: `/usr/bin/time -l`, the process's user and kernel instructions, so `wait`
# holds the kernel's work for its two `kevent` calls too, and a macOS update may move it. Taken on
# `mac`, an Apple M1 Pro on macOS 26.6.2, on 2026-09-30, at a load average of about 22; four runs
# agreed within 0.2 percent.
#
# linux-*: Valgrind's cachegrind, user instructions only, the same on every run. Printed by CI run
# 36671917366 on commit d187080, 2026-09-30, with Valgrind 3.22.0: x86-64 on an AMD EPYC 7763,
# arm64 on an Arm Neoverse N2 (CPU part 0xd49). The arm64 counts matched, workload for workload, a
# run under Valgrind 3.23.0 in an arm64 container on `mac`. io_uring has no `wait`: its loop has no
# call that wakes itself.
#
# linux-aarch64-uring `timer` was set from 1004 to 1025 on 2026-11-05, by Camilo's choice, after
# 06549d2 made the loop split coalesced datagrams (decision 15). The workload splits nothing. The 19
# instructions over the tree before it, which counted 1006, are the reap's check for a pending split
# and a different layout of the tick's code that no line of the split explains. CI run 42149102186
# and an arm64 container on `mac` both counted 1025.
#
# macos-aarch64-kqueue `post-operation`, `timer` and `batch` were raised on 2026-11-06, by Camilo's
# choice, for decision 26: a program that names no record pays about 6 instructions in each tick,
# 8 at each operation's submit and 2 at each event. The tree before it counted 2988, 1086 and
# 24189 on `mac`. Cachegrind on arm64 Linux counted +0.6 to +1.0 percent on io_uring and +1.0 to
# +2.1 percent on epoll for the same change.
#
# The linux-* rows that CI run 42270575393 counted over the tolerance at d1657ce, decision 26, were
# raised to its counts on 2026-11-06, by Camilo's choice. Against the parent b4a8c5b (run
# 42262757947) the change cost +0.5 to +2.8 percent; several rows failed because the parent already
# sat 1.5 to 1.8 percent over them. The two epoll `wait` rows were lowered to that run's counts, as
# the gate asked.
#
# `task` and `tasks-64` were added on 2026-11-06 for decision 27: one tick that runs one task, and
# one that runs `tasks_per_tick_max` tasks. The macOS rows are from `mac`, and the linux-aarch64
# rows from cachegrind in an arm64 container on `mac`. The linux-x86_64 rows are the counts that
# CI's x86-64 runner printed at `000e981`, because an x86-64 container on `mac` cannot start a
# loop. The same day `work.zig` began to compile one loop for each workload, because with one
# switch inside one loop the two new workloads made `post` count 15 more instructions with no
# change to rotor.
#
# `record` and `poller` were added on 2026-11-06 for decision 26: one timer whose event goes to its
# record, and one tick with one poller that reports no work. Both take `tick_dispatched`, the cold
# path of decision 7, row H1, which no row held before. The macOS rows are from `mac`, where four
# runs agreed within 3 instructions at a load average of 14 to 22. The linux-aarch64 rows are from
# cachegrind in an arm64 container on `mac`. The linux-x86_64 rows are the counts that CI's x86-64
# runner printed at `c045266`, run 42306194680. The same day each workload's loop
# became a function of its own, because the two new loops inside `main` made epoll's `tasks-64`
# count 63 more instructions. With that change every older row counted within 3 instructions of the
# tree before it.
#
# `task` and `tasks-64` were raised on 2026-11-06 for decision 28, by Camilo's ruling 2 of that
# record: the loop stores the name of each callback before it calls it, so a watch can name the
# one that holds the loop. Each tick also compares its turn with the stall threshold. The counts
# are from the tree after the optimisation of 2026-11-06, before the `noinline` turn check of
# ledger row H5, which counts 3 fewer on arm64 Linux and the same on `mac`. On `mac` they are the
# median of three runs that agreed within 2 instructions, and on arm64 Linux, cachegrind in an
# arm64 container on `mac`. The linux-x86_64 `task` and `tasks-64` rows are deleted, so CI prints
# them.
#
# The rows that decision 28 moved past the tolerance were raised on 2026-11-06 to the counts of
# the final tree, with H5, by Camilo's ruling 2 of that day. For each row, the list gives the count
# at c05913b, the tree before decision 28, and the line before: macos `post` 1231 and 1218, `poller`
# 573 and 570; linux-aarch64-uring `post` 1043 and 1029, `record` 1134 and 1128, `poller` 501 and
# 497; linux-aarch64-epoll `post-operation` 3059 and 3019, `record` 1196 and 1191, `poller` 580
# and 574. The cause is the stamp and the turn check of each tick, and the name that the loop
# stores before each callback: +1.0 to +3.0 percent on these rows. Each `poller` row moved past
# the tolerance by itself. Each other row sat 0.4 to 1.4 percent over its line at c05913b, and the
# change took it past. The counts are taken as for `task`. The linux-x86_64 `poller` rows are
# deleted, because `poller` moved 3.0 percent on arm64 io_uring and 2.6 on epoll. So are the
# linux-x86_64 rows of each other row raised on arm64: io_uring `post` and `record`, and epoll
